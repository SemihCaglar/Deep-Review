## Account onboarding, approvals, and email-reset assumptions

The system assumes that it starts with one seeded bootstrap coordinator account so that user onboarding can begin without a circular dependency. Regular users do not become active immediately after registration; instead, they sign up through the frontend and remain in `Pending` status until a coordinator explicitly approves or rejects them. Only approved users are allowed to log in and appear in the `Lab Members` page. The coordinator manages this process through the dedicated `Pending Approvals` page, which includes both the current pending requests and an approval history section for previously reviewed requests. The seeded bootstrap coordinator is intentionally visible in `Lab Members` as part of the lab, but is excluded from `Approval History` because that account is created through seed/bootstrap rather than through the ordinary signup-review workflow.

The password reset flow assumes that a shared backend email service is configured and available. Reset requests generate a secure reset link using `FRONTEND_BASE_URL`, and this link is sent to the user through the configured SMTP-backed email delivery mechanism. Only the hashed token is stored in the database. The API keeps the generic success response to avoid leaking whether an account exists. In local development, successful delivery does not guarantee inbox placement; reset emails may arrive in the spam folder when using development-grade mail configuration such as Gmail SMTP without production email reputation and domain authentication.

## Local execution and environment configuration assumption

The system is assumed to be run locally as two separate processes: a backend service and a frontend service. The backend must be started first, since the frontend depends on the backend API for authentication, profile loading, signup approval, and password-reset operations. Before running the backend, dependencies must be installed and the seed script must be executed so that the default topics and the bootstrap coordinator account are created. The backend is then started with `JWT_SECRET` and, when email-based password reset is being tested, with additional mail-related environment variables such as `FRONTEND_BASE_URL`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, and `SMTP_FROM`. The frontend is started separately after installing its dependencies, and it is assumed to run on a local development port such as `http://localhost:3000`. If old browser authentication data exists, local storage should be cleared before testing so that expired or stale tokens do not affect the observed system behavior.
